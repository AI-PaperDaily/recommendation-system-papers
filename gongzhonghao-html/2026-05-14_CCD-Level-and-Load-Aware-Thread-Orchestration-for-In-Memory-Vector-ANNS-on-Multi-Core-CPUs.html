CCD-Level and Load-Aware Thread Orchestration for In-Memory Vector ANNS on Multi-Core CPUs

📅 2026-05-14

小红书突破向量检索性能瓶颈：CCD感知线程编排最高提升3.7倍吞吐量

在搜索、推荐和广告等核心业务场景中，向量近似最近邻搜索（ANNS）是支撑海量数据实时检索的基石。随着小红书等平台月活用户数亿，每秒需要处理数千万条查询请求（QPS），对延迟和吞吐量的要求极为严苛。然而，当业务规模持续增长，单纯的CPU核数增加却带来了性能提升递减的困境。

日前，小红书（RedNote）技术团队联合学者在一篇研究论文中揭示了这一问题的根源，并提出了一套面向现代CCD（Core-Complex Dies）架构多核CPU的线程编排框架。实验数据表明，该方案在小红书真实生产负载下，吞吐量最高提升3.7倍，P50和P999延迟分别降低30%-90%，L3缓存缺失率降低6-30%，CPU停顿周期减少20-80%。

一、核心方法

1.1 痛点剖析：为什么“加核”不再奏效？

现代CPU厂商（如AMD的EPYC系列）通过CCD架构扩展核心数：将多个核心与共享的L3缓存封装在一个芯粒（Chiplet）内。与传统的单芯粒CPU不同，CCD架构下每个CCD拥有独立的L3缓存，这些缓存仅对该CCD内的核心可见且访问延迟低。

研究者在分析小红书线上生产负载后发现三个关键瓶颈：

  1. 局部性被浪费：短时间内，查询同一向量表的请求倾向于访问重叠的子集，呈现出强内存局部性。但原有调度机制未利用这一点。
  2. 缓存污染严重：不同CCD的L3缓存相互独立，不当的任务分发会导致一个CCD内缓存被多个“热表”的数据反复冲刷（即“热-热”同置）。
  3. 负载失衡加剧：不同向量表的搜索开销差异巨大（呈重尾分布），而跨CCD窃取任务带来的缓存污染反而进一步恶化性能。

1.2 技术架构：统一接口与CCD感知调度


图1：整个框架作为一个“插拔式”层，介于向量索引和后端CPU硬件之间，包含任务提交、任务分发与监控、以及线程编排三大模块。

论文引入的三层架构设计如下：

1. 统一任务提交接口

框架为HNSW（图索引）和IVF（聚类索引）两种主流ANNS索引定义了统一的submit(search_functor, query, Mapping_ID)接口。通过将HNSW的表ID和IVF的聚类列表ID抽象为统一的Mapping_ID，实现了代码层的零侵入替换。

2. 任务分发器与工作负载监控器

这是框架的核心大脑。它维护一张从Mapping_ID到CCD的映射表，并遵循两条原则：
- 亲和性：同一热表的所有查询任务始终分发到同一个CCD，以利用局部L3缓存。
- 热-冷配对：通过算法1（平衡热-冷配对）避免将两个高流量热表放在同一个CCD，而是将热表与冷表配对，分散内存流量压力。


图2：对比“热-热同置”（左）和“热-冷配对”（右）。当两个热表同在一个CCD时，彼此的查询会交替冲刷对方在L3缓存中的数据，导致缓存缺失率飙升。而将热表与一个冷表配对，冷表几乎不占用缓存资源，热表的工作集得以稳定驻留。

该映射并非静态的。工作负载监控器会实时估算每个搜索任务的内存流量开销，并定期（如每分钟级别）触发快照式重映射。新映射发布时，旧任务继续使用当前映射完成，无中断切换。

其中，内存流量的近似估算公式如下：

$$T_{\mathrm{HNSW}} \approx N \cdot (B_v + M \cdot s_{\mathrm{id}}) + \delta_{\mathrm{meta}}$$

  • $N$：HNSW搜索中访问的节点数
  • $B_v = D \cdot s_v$（$D$为向量维度，$s_v$为每个元素的字节数，例如FP32为4）
  • $M$：每个节点的出度（邻居数）
  • $s_{\mathrm{id}}$：节点ID的字节宽度（通常为4字节）

对于IVF，扫描单个聚类列表$\mathcal{L}_i$的流量为：

$$T_{\mathrm{IVF}}(\mathcal{L}_i) \approx S_i \cdot B_v$$

其中$S_i = |\mathcal{L}_i|$为该列表中被扫描的向量数量。

3. CCD感知的任务窃取

即便有了智能分发，负载失衡仍可能发生。为解决此问题，论文提出了一种拓扑感知的任务窃取策略。每个工作线程优先从本地队列获取任务，次优先从同一CCD内的其他核心窃取任务（保留缓存亲和性），最后才考虑跨CCD窃取。


图3：核心X若从同一CCD的核心0窃取任务Q0，数据已在本地L3缓存中；若从其他CCD的核心Y窃取任务Q1，则远程缓存中的数据几乎无效，需重新从内存加载。

该算法的核心逻辑如Algorithm 2所示：PopLocal → TrySteal(同CCD) → TrySteal(跨CCD)。实验表明，该方法将跨CCD的窃取比例从V1基线中的75-80%大幅降低至5-10%。

二、实验成果

研究者在两代AMD EPYC处理器上进行评估：

配置 第4代EPYC (Genoa) 第2代EPYC (Rome)
核心数 96核 (12 CCD) 48核 (12 CCD)
每CCD缓存 32MB L3 (8核/CCD) 16MB L3 (4核/CCD)
内存 576GB DDR5 512GB DDR4

2.1 吞吐量提升与延迟优化


图4：在96核CPU上，新框架（V2）的HNSW吞吐量随CCD数近乎线性增长，达到100K QPS以上，相比V1（bthread）和V0（轮询）保持明显优势。

对于IVF，V2在96核上同样实现约35K QPS的饱和吞吐量，而V1约为25K QPS，V0仅约10K KQPS。

延迟层面，V2在所有测试向量表上均取得最低的P50和P999延迟。对于HNSW，部分表的P999延迟从V0的数毫秒降至V2的0.5毫秒以内。

2.2 微观指标拆解

  • L3缓存缺失率：V2在12个CCD上一致地低于V1和V0，证明热-冷配对和CCD感知窃取有效降低了缓存污染。
  • CPU停顿：图19(a)显示V2的CPU停顿周期显著低于V1，意味着核心更多时间在执行有效计算而非等待内存。
  • 跨CCD窃取比例：如前所述，V2将跨CCD窃取从75-80%骤降至5-10%，保住了宝贵的缓存命中率。

三、结语

小红书技术团队提出的这一方案，揭示了在现代CCD多核CPU架构上，“软件感知硬件” 的协同设计能释放巨大的性能潜力。当向量搜索的强内存局部性遇到独立L3缓存的CCD架构，简单轮询或任务窃取已不足以应对日益增长的业务压力。

通过统一的接口层、动态的热-冷映射以及拓扑感知的任务窃取，研究者成功地将硬件升级的红利真正转化为线上服务的吞吐量提升。

这给业界一个深刻的启示：在芯片设计日趋复杂化的今天，系统软件栈必须打破“硬件透明”的传统思维，主动为硬件拓扑高度优化，才能实现百核级CPU的应有价值。
