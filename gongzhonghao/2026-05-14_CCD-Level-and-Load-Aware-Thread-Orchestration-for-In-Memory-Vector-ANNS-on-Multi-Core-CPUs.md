# 小红书3.7倍吞吐量突破：CCD感知的向量检索线程编排，让96核CPU性能最大化？

在大模型和搜索推荐系统蓬勃发展的今天，**向量近似最近邻搜索（ANNS）** 已经成为支撑搜索引擎、推荐系统和广告服务的核心基础设施。然而，随着业务规模的持续扩张，一个现实问题摆在工程师面前：**为什么CPU核心数不断增加，向量检索的性能却无法线性提升？**

近日，小红书（RedNote）的研究团队发表了一篇引人瞩目的论文，深入剖析了现代多核CPU架构下向量检索的性能瓶颈，并提出了一套**CCD级别、负载感知的线程编排框架**。在真实生产环境中，该方法带来了**高达3.7倍的吞吐量提升**，并将P50和P999延迟分别降低了**30%和90%**。本文将深度解析这项技术的核心原理与实现细节。

## 一、背景与痛点：现代CPU的“多核陷阱”

随着工艺极限的到来，传统单芯片CPU（Monolithic CPU）已难以大规模扩展核心数量。因此，现代服务器CPU（如AMD EPYC系列）普遍采用**CCD（Core-Complex Die，核心复杂芯片）架构**。

![图1：单芯片CPU与CCD多芯片CPU对比](https://arxiv.org/html/2605.10090v1/x4.png)
*图注：CCD架构下，每个芯片拥有独立的L3缓存，这带来了新的局部性挑战。*

与传统单芯片设计不同，CCD架构将多个核心打包在一个芯片上，每个芯片拥有自己独立的**末级缓存（LLC/L3）**。这种设计带来了两个关键问题：
1.  **无共享LLC**：跨CCD访问数据将导致缓存缺失和远程内存访问延迟。
2.  **任务调度与缓存局部性失配**：若不加优化地调度向量搜索任务，极易造成CCD间的缓存污染和内存带宽争抢。

研究人员对小红书线上的HNSW和IVF索引进行测试后发现，**简单增加CPU核心数**（从16核到96核），实际吞吐量仅达到理想值的82%，且IVF索引的缩放效率更差。

## 二、核心洞察：生产环境中向量请求的“热点”与“偏斜”

为了探寻效率低下的根源，研究者深入分析了实际生产环境的请求特征。

**发现一：请求存在显著的访问局部性。**
在短时间内，连续查询往往会反复访问图中相同的节点或IVF中的相同聚类列表。如图2所示，无论是HNSW还是IVF，其访问频率分布都呈现出**长尾效应**：少量热点节点/列表承担了绝大部分的查询流量。

![图2：搜索访问频率分布](https://arxiv.org/html/2605.10090v1/x10.png)
*图注：HNSW和IVF的访问都呈现出高度集中的热点分布。*

**发现二：内存流量高度不均衡。**
不同向量表、不同聚类的内存访问量差异巨大，有的表流量可达上千MB，而其他表则仅有几十MB。这种**偏斜性**在CCD架构下尤为致命：如果把多个“热”表映射到同一个CCD上，它们的频繁访问会互相竞争有限的L3缓存，导致缓存污染和频繁的缓存置换，严重影响性能。

研究人员明确指出：“将多个热表放置在同一CCD上，会造成热–热共置，导致缓存污染；而热–冷共置则可以让热点的数据驻留在缓存中。”

## 三、突破性框架：CCD级别的线程编排优化

基于上述洞察，小红书提出了一套名为 **“CCD-Aware Thread Orchestration”** 的框架，核心思想是让**任务调度与CPU的物理拓扑结构对齐**，从而实现缓存局部性的最大化。

![图3：CCD级线程编排框架全景图](https://arxiv.org/html/2605.10090v1/x16.png)
*图注：框架包含三大模块：CCD级任务提交、任务分发与工作负载监控、CCD感知的任务窃取。*

### 1. 缓存友好的任务分发与动态适应

框架的核心组件是**任务分发器**和**工作负载监控器**。它的目标是：**将一个热点表（或聚类）的请求尽可能调度到同一个CCD上，同时避免在同一CCD上堆积多个热点**。

为此，研究者提出了一个**热–冷配对算法**（Hot–Cold Pairing）。算法首先估算每个HNSW表或IVF聚类的“内存流量”，然后通过贪心策略，将最大的热项与最小的冷项配对，并分配到同一CCD，从而平衡各CCD间的负载，最大化缓存命中率。

更精妙的是，系统会**实时监控请求动态**，并在一定时间窗口（如分钟级）后，通过“快照交换”机制平滑地更新CCD与任务之间的映射关系，以应对流量的波动。

**公式解读：内存流量估算**

论文中给出了内存流量的近似估算公式，这对理解调度策略至关重要：

对于 **HNSW** 索引，一次查询的内存流量 $T_{\mathrm{HNSW}}$ 约为：
$$T_{\mathrm{HNSW}}\;\approx\;N\cdot\big(B_{v}\;+\;M\cdot s_{\mathrm{id}}\big)$$
其中，$N$ 是查询访问的节点数，$B_{v}$ 是向量数据大小，$M$ 是节点的出度，$s_{\mathrm{id}}$ 是节点ID的字节数。

对于 **IVF** 索引，对于某个聚类列表 $\mathcal{L}_{i}$ 的流量 $T_{\mathrm{IVF}}(\mathcal{L}_{i})$ 为：
$$T_{\mathrm{IVF}}(\mathcal{L}_{i})\;\approx\;S_{i}\cdot B_{v}$$
其中，$S_{i}$ 是该聚类列表中的向量数量，$B_{v}$ 为单个向量的大小。

这两个公式为调度器提供了量化每个任务“内存代价”的依据，从而做出更优的CCD分配决策。

### 2. CCD感知的拓扑优化任务窃取

即使是精心设计的初始调度，也难以避免核心间的负载不均衡。传统的“任务窃取”机制（Work Stealing）虽然能解决这一问题，但在CCD架构下会带来新问题：**跨CCD窃取任务会导致线程访问远端CCD的L3缓存，造成巨大的缓存缺失**。

为了避免这种“赔了夫人又折兵”的情况，研究团队设计了**CCD-Aware任务窃取**策略。该策略核心思想非常简单但有效：
- **优先从同一CCD内的核心窃取任务**，以保留LLC命中。
- **只有在同一CCD内所有核心空闲时，才考虑跨CCD窃取**。

实验数据显示，这一策略极其成功。对于HNSW，跨CCD窃取的比例从原始的75%降低到不足10%；对于IVF，比例更是从超过80%降至仅5%。

## 四、实战效果：3.7倍性能提升与90%延迟下降

论文在AMD的两种CCD架构CPU（第2代48核和第4代96核）上进行了详尽测试，使用的都是来自小红书的真实生产负载。

![图4：HNSW和IVF的饱和吞吐量对比](https://arxiv.org/html/2605.10090v1/x21.png)
*图注：在小红书的真实生产负载下，新框架V2（CCD-aware）的吞吐量远超V0和V1。*

实验结果显示：
- **吞吐量**：在96核CPU上，HNSW索引的吞吐量超过100K QPS，IVF索引达到35K QPS，相比之前的V1（bthread）和V0（baseline）均有显著优势，性能提升高达 **3.7倍**。
- **延迟**：P50和P999延迟大幅降低。与V1相比，V2在多个HNSW表上实现了 **30-90%的延迟降低**，整体服务端到端延迟分布更加稳定，抖动更小。
- **缓存与计算效率**：L3缓存的缺失率降低了 **6-30%**，CPU因等待数据而停滞的周期减少了 **20-80%**，这意味着CPU资源被更充分地用于实际计算。

## 五、展望：硬件-软件协同设计的新范式

这项来自小红书的工程实践，不仅解决了向量检索在新型CPU架构下的性能瓶颈，更提供了一种**硬件-软件协同设计的全新范式**。

未来的计算系统将越来越复杂，多芯片、非一致性内存访问（NUMA）将成为常态。小红书的研究向业界展示了，**只有深刻理解硬件拓扑，并将这种认知融入上层调度系统，才能真正释放现代CPU的所有潜力**。

对于正在或即将部署大规模向量检索服务的团队而言，这篇文章无疑提供了一个极具价值的优化方向。在追求“堆核”的同时，是时候思考如何让这些核心“更聪明地”工作了。
